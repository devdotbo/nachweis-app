## 1. Privy: wallets, SDK, chains

- Node SDK: `@privy-io/node` 0.34.0 latest on npm (FACT, registry.npmjs.org). Older `@privy-io/server-auth` 1.32.5; `@privy-io/react-auth` 3.40.0; `@privy-io/wagmi` 4.0.17 (FACT, same source). The node-sdk README (github.com/privy-io/node-sdk, updated 2026-09-08): "Bun 1.0 or later" supported; "Web browser runtimes aren't supported. The SDK will throw an error if used in a browser environment." (FACT)
- Client construction (FACT, https://docs.privy.io/basics/nodeJS/setup and /quickstart): `import {PrivyClient} from '@privy-io/node'; const privy = new PrivyClient({appId: 'insert-your-app-id', appSecret: 'insert-your-app-secret'});`
- Wallet creation (FACT, https://docs.privy.io/wallets/wallets/create/create-a-wallet): `privy.wallets().create({chain_type: 'ethereum', owner: {...}})`; parameters `owner` (authorization key P-256 public key, user id, or key quorum id via `owner_id`), `policy_ids`, `additional_signers`. "You must use a server-side SDK to create wallets owned by an authorization key."
- Send transaction (FACT, quickstart): `privy.wallets().ethereum().sendTransaction(walletId, {caip2, params: {transaction: {to, value: "0x1", chain_id: 11_155_111}}})`; Sepolia appears as the example chain id. Send page: "a successful response indicates that the transaction has been broadcasted to the network".
- Sign only (FACT, https://docs.privy.io/wallets/using-wallets/ethereum/sign-a-transaction): `privy.wallets().ethereum().signTransaction(walletId, {params: {transaction: {to, value, chain_id}}})` returns `signed_transaction`. Search snippet of the server-wallet guide: "you can prepare and broadcast the transaction yourself, and simply use eth_signTransaction (EVM) ... to sign the transaction with a server wallet" (CLAIM, search snippet, page itself not fetched). Whether Privy signs for chain id 31337 (anvil) and whether policy `chain_id` conditions evaluate for an unknown chain: unverified.
- Chains (FACT, https://docs.privy.io/wallets/overview/chains): broadcasting tier "Ethereum (including EVM-compatible networks)"; no explicit Sepolia or custom-chain sentence on that page. Treasury page: "all EVM chains, all SVM (Solana) chains, Tempo, Bitcoin, Spark, Tron, Stellar, and more."

## 2. Privy: policies

- Overview (FACT, https://docs.privy.io/controls/policies/overview): "Privy's policy engine gives your application programmable control over how every wallet can be used." Structure policy, rules, conditions. "If no rules resolve, the policy will default to DENY." Capabilities listed: "Transfer limits", "Allowlists and denylists of transfer recipients", "Allowlists and denylists of smart contracts", "Granular constraints around calldata and parameters".
- Create (FACT, https://docs.privy.io/controls/policies/create-a-policy): dashboard, SDK, or `POST https://api.privy.io/v1/policies`; Node: `privy.policies().create({name, version: '1.0', chain_type: 'ethereum', rules: [...], owner_id: '<key quorum id>'})`. "Without an owner, the policies can be updated by your app secret alone." Attached to wallets through `policy_ids` at creation or update.
- API reference (FACT, https://docs.privy.io/api-reference/policies/create): Ethereum rule `method` enum includes `eth_sendTransaction`, `eth_signTransaction`, `eth_signUserOperation`, `eth_signTypedData_v4`, `personal_sign`, `eth_sign7702Authorization`, `wallet_sendCalls`, `*`. `field_source` values: `ethereum_transaction`, `ethereum_calldata`, `ethereum_typed_data_domain`, `ethereum_typed_data_message`, `ethereum_7702_authorization`, `system`, `action_request_body`, `reference`, `message`. Operators: `eq`, `gt`, `gte`, `lt`, `lte`, `in`, `in_condition_set`, `contains`, `starts_with`, `ends_with`. Rule: `name` (1 to 50 chars), `method`, `conditions`, `action` `ALLOW` or `DENY`. ABI schemas capped at 200 items.
- Examples (FACT, https://docs.privy.io/controls/policies/example-policies/ethereum): calldata condition `{"field_source": "ethereum_calldata", "field": "transfer.amount", "abi": [...transfer(address recipient, uint256 amount)...], "operator": "lte", "value": "0x2386F26FC10000"}`; transaction condition `{"field_source": "ethereum_transaction", "field": "to", "operator": "eq", "value": "0x8335...2913"}`; a `function_name` field with `operator: eq` allows a named function; chain restriction examples exist (single and multiple chains).
- Condition sets (FACT, https://docs.privy.io/controls/policies/condition-sets): "reusable lists of values that can be referenced in policy conditions"; `POST /v1/condition_sets`, items via `/v1/condition_sets/{id}/condition_set_items`; referenced with operator `in_condition_set`; updates need an owner's authorization signature.
- Stateful policies (FACT, https://docs.privy.io/controls/policies/stateful-policies): aggregations over time windows; rule uses `field_source: "reference"`, `field: "aggregation.<id>"`; "each app can have a maximum of 10 aggregations"; "Aggregation values are updated after a request is successfully signed, not before".
- Enforcement (FACT, https://docs.privy.io/security/wallet-infrastructure/policy-and-controls): "By default, the trusted execution environment (secure enclave) enforces policies when processing wallet actions, such as signature requests, transactions, and key export." Some policies (transfer size limits requiring simulation) run at the API level (summarised).
- Transfer action policies (FACT, https://docs.privy.io/wallets/actions/transfer/policies): method `transfer`, `field_source: action_request_body`, fields `source.asset`, `source.amount`, `source.chain`, `destination.address`, etc.

## 3. Privy: key quorums, intents, organizations, manual approvals

- Key quorum concept (FACT, https://docs.privy.io/controls/authorization-keys/owners/types): owners and signers are users, authorization keys ("P256 cryptographic keys"), or key quorums ("a mix of users and authorization keys"); "Key quorums have an authorization threshold that defines how members of the quorum must sign a request for the aggregated signature to be valid."
- Create (FACT, https://docs.privy.io/controls/key-quorum/create): `privyClient.keyQuorums().create({public_keys: ['authorization-key'], user_ids: ['user-id'], display_name: '2 of 2 Test Key Quorum', authorization_threshold: 2})`; "The returned id for the key quorum is used as the owner_id field when creating or updating resources (e.g. wallets or policies)." Dashboard: Wallets, Authorization keys, New key, "Register key quorum instead". Mixed user plus key quorums via REST only.
- Sign with a quorum (FACT, https://docs.privy.io/controls/key-quorum/sign): "Pass the signatures as a comma-delimited string in the privy-authorization-signature header"; Node: `authorization_context: {authorization_private_keys: [...], user_jwts: [...]}`.
- Quorum approvals setup (FACT, https://docs.privy.io/transaction-management/setups/quorum-approval): "Privy's TEE infrastructure enforces that at least that many members of the quorum must sign the request to take an action with a wallet."
- Intents (FACT, https://docs.privy.io/transaction-management/intents/overview): "Intents let your app propose an action on a wallet or resource, then collect the authorization signatures needed to execute it separately, over time and, if needed, from multiple parties." Actions: transfers, RPC transactions, wallet updates, policy updates, key quorum updates. "Manual approvals is Privy's Dashboard-native implementation of intents".
- Create an RPC intent (FACT, https://docs.privy.io/transaction-management/intents/create/execute-rpc): `const intent = await client.intents().rpc('insert-wallet-id', {method: 'eth_sendTransaction', caip2: 'eip155:8453', sponsor: true, params: {transaction: {to, value}}})`; default expiry 72 hours.
- Authorize (FACT, https://docs.privy.io/api-reference/intents/authorize): `POST /v1/intents/{intent_id}/authorize` with body `{signature, timestamp}`; "Can be called by the wallet owner (via user token) or with the app secret." Java SDK: `client.intents().authorize(intentId, authorizationContext)`; the Node method name was not shown on the sign-intents page (unverified; the changelog for 0.13.0 says "Introduced IntentService for manual approval workflows via privy.intents").
- Lifecycle (FACT, https://docs.privy.io/transaction-management/intents/lifecycle): states Pending, Granted, Processing, Executed, Failed, Rejected, Expired, Dismissed; Failed causes include "a policy blocking the transaction or insufficient gas or balance to transact".
- Manual approvals in the dashboard (FACT, https://docs.privy.io/controls/dashboard/overview): "Manual approvals is an Enterprise feature." "Reach out to sales@privy.io to request access for your app." This gates the dashboard review UI; the intents API pages carry no such sentence (checked overview, lifecycle, execute-rpc, authorize). Whether a free app can create and authorize intents through the API: unverified.
- Organizations (FACT, https://docs.privy.io/organizations/overview): "Privy powers programmable wallets for organizations, allowing multiple people to securely hold funds, manage access, and operate financial workflows together." Developers build "payments platforms, banking products, payroll systems, and spend management tools" (summarised). Approvals page: "Once a sufficient threshold of signatures has been collected, Privy will automatically execute the intent." No availability sentence on the overview or setup pages (checked).
- Treasury solution page (FACT, https://docs.privy.io/wallets/overview/solutions/treasury-wallets): key quorums "m-of-n signers to authorize a transaction before it executes"; policies "ensure guardrails for spend and usage by your treasury team"; workflows "balance sweeps, liquidity rebalancing, disbursement triggers, and reconciliation".

## 4. Privy: pricing and plan gates (the top risk)

- https://www.privy.io/pricing (FACT, fetched twice 2026-09-09): Core plan free, "50K signatures/month", up to 499 MAU, "$1M transaction volume/month". Feature matrix: "Security & Compliance, Policy engine, Key quorum approvals, Advanced SSO, Available as add-on, Custodial wallets". Both fetches read the policy engine and key quorum approvals as "Available as add-on" for the non-Enterprise plans. The page does not say whether an add-on is switched on in the dashboard or requires sales. Enterprise: "To upgrade to an Enterprise plan, please contact sales@privy.io".
- Webhooks (FACT, https://docs.privy.io/wallets/actions/webhooks): "To enable webhooks in production, upgrade to the Enterprise plan"; free plan restricted to development environments (summarised). Events cover transfer, swap, payout, earn; not plain RPC transactions.
- Consequence: the case must run with a policy and a key quorum if the add-on can be enabled on a free app in the morning, and must have a fallback that still uses a Privy wallet if it cannot. See case.md sections 7 and 9.

## 6. Law and market: why the workflow is blocked today

- German Civil Code, English translation (FACT, https://www.gesetze-im-internet.de/englisch_bgb/englisch_bgb.html): Section 106 "A minor who has reached the age of seven has limited capacity to contract under sections 107 to 113." Section 107 "For a declaration of intent as a result of which minors do not receive merely a legal benefit, the minors require consent by their legal representative." Section 108(1) "If the minor enters into a contract without the necessary consent of the legal representative, the effectiveness of the contract is subject to approval by the legal representative." Section 113 covers service or employment authorised by the legal representative.
- Council Directive 94/33/EC on the protection of young people at work (FACT for existence, https://eur-lex.europa.eu/eli/dir/1994/33/oj/eng; content summarised from EU-OSHA and Commission pages, CLAIM): member states must prohibit work by children, minimum age not lower than the end of compulsory schooling or 15; applies to any person under 18 with an employment contract or relationship.
- AMLR, Regulation (EU) 2024/1624, Article 3 obliged entities (FACT, https://amlr.eu/article-3-obliged-entities/, secondary mirror of the text): credit institutions, financial institutions, and the listed professions (auditors, notaries, trust or company service providers, estate agents, dealers in precious goods, gambling providers, crowdfunding providers, cultural goods, credit intermediaries, investment migration operators, mixed activity holding companies, football agents and clubs). No item covers employers, payroll providers or businesses paying contractors. Crypto-asset service providers are financial institutions under Art 2(1)(6)(i) (FACT via /Users/bioharz/git/ethglobal/nachweis/raw/2026-09-06-product-pitch-legal.md line 109).
- Transfer of Funds Regulation, Regulation (EU) 2023/1113 (FACT, https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32023R1113): Art 14(5) "In the case of a transfer of an amount exceeding EUR 1 000 to a self-hosted address, the crypto-asset service provider of the originator shall take adequate measures to assess whether that address is owned or controlled by the originator." Art 16(2) mirrors it for the beneficiary's CASP. Scope Art 2(1): applies where a CASP of the originator or beneficiary is in the Union. A company paying from its own wallet without a CASP is outside this duty; a payroll provider that is a CASP is inside it.
- eIDAS 2, Regulation (EU) 2024/1183, Art 5f(2) (FACT, https://www.european-digital-identity-regulation.com/Article_5a_(Regulation_EU_2024_1183).html): "Where private relying parties that provide services, with the exception of microenterprises and small enterprises ..., are required by Union or national law to use strong user authentication for online identification or where strong user authentication for online identification is required by contractual obligation, including in the areas of transport, energy, banking, financial services, social security, health, drinking water, postal services, digital infrastructure, education or telecommunications, those private relying parties shall, no later than 36 months from the date of entry into force of the implementing acts referred to in Article 5a(23) and Article 5c(6) and only upon the voluntary request of the user, also accept European Digital Identity Wallets". Derived dates per the legal memo: wallets by 2026-12-24, acceptance by 2027-12-24 (FACT via memo line 171).
- GDPR Art 5(1)(c) data minimisation and EDPB Guidelines 02/2025 on blockchains (FACT via memo line 116; predicate bits bound to an address remain personal data in the EDPB reading).
- Legal memo boundary (OPINION in the memo, /Users/bioharz/git/ethglobal/nachweis/raw/2026-09-06-product-pitch-legal.md lines 137 to 140): "A predicate proof is legally sufficient wherever the duty is defined by the predicate: age, residency, nationality, jurisdiction, address control"; not sufficient for customer due diligence under AMLR. Row 7 of the same memo already lists "Payee verification in a project escrow" with "Paying agency (tax, worker classification), not an AMLR obliged entity", scored 1, 1, 2 for demand, crypto appeal and EUDI add.
- Market practice (CLAIM, https://www.riseworks.io/blog/how-to-pay-international-freelancers-in-crypto, dated 2026-09-08 on the page): "Each freelancer must complete KYC verification and submit the relevant tax forms"; the freelancer "connects a self-custody wallet ... or uses a platform-managed wallet"; verification is done to "comply with KYC and AML rules". Paybis states a MiCA CASP authorisation from the Bank of Latvia, May 2026 (CLAIM, search snippet).
- Platform Work Directive (EU) 2024/2831, transposition by 2026-12-02 (FACT for the date, EUR-Lex summary via search); no age or identity verification article found in the search results: unverified, not relied on.
- DAC7, Directive (EU) 2021/514 (CLAIM, search snippets): platforms must collect name, address, date of birth for individual sellers and verify reliability. Used only in the rejected-variants section.
