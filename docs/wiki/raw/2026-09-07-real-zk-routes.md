## 2. Recommendation

Primary: R1. Fallback: R4 (start its kill test in parallel on Sep 8 because it is small). Do not build R2 or R3. R5 stays the side clip already planned.

Why R1: it is the only route where the ZK statement is about the real sandbox PID from the official wallet, it lives entirely in Rust, and it changes the trust model of the product rather than adding an exhibit. Today the registry entry means "Nachweis says so". After R1 it means "a valid PID under the sandbox trust anchor, holder-bound to this wallet, over 18, was verified; the chain checked the proof". The operator can no longer mint eligibility for an address that never presented a PID (soundness), and nobody learns anything beyond the bits (zero-knowledge). OPINION.

Sentence for camera (true if R1 ships): "The chain does not trust our server. It verifies a zero-knowledge proof that a PID from the official German sandbox wallet, signed under the sandbox trust anchor and bound to this wallet, was checked and says over 18. Names never enter the proof and never touch the chain. The proof is generated by our verifier, not yet by the phone; no wallet in the sandbox can prove on-device today."

What the chain sees: a Groth16 proof (about 260 bytes), the program verification key, and ABI-encoded public values: sha256 of the trust anchor DER, vct hash, over18 bit, bound address, nonce, expiry. It does not see the SD-JWT, the disclosures, the issuer certificate, or the KB-JWT.

Fallback sentence (R4): "This proof was generated on the phone by an open-source wallet with Google's Longfellow circuits and verified fail-closed by our verifier; the credential is a test credential because the German sandbox wallet cannot prove yet."

## 3. R1 build plan

Dependency check against klartext-verifier/verifier-core/Cargo.toml (FACT, read 2026-09-07):
- verifier-core depends on openid4vp (spruceid git), ssi 0.16, josekit (cobward fork), x509-cert 0.2.4, p256 0.13, sha2 0.10, chrono, serde_json. Cargo.lock also carries openssl, ring, tokio, reqwest; `cargo tree --offline` failed on this machine ("no matching package named base64"), so which of those reach verifier-core is unverified. Verdict: do not compile verifier-core in the guest. ssi and openid4vp are heavy and untested on riscv32; josekit is only used for JWE decryption (crypto.rs:13-30), which stays in the host.
- What ports directly: trust.rs (p256 ecdsa Verifier plus x509-cert der, lines 17-24) and the hashing in crypto.rs. Both trust anchors in fixtures/oracle are ecdsa-with-SHA256 on prime256v1 (FACT, openssl), so the chain check is one more P-256 verify and no RSA is needed.
- Patched crates match the workspace versions: SP1 `p256 = { git = "https://github.com/sp1-patches/elliptic-curves", package = "p256", tag = "patch-p256-13.2-sp1-6.0.0" }` and `sha2 = { git = "https://github.com/sp1-patches/RustCrypto-hashes", package = "sha2", tag = "patch-sha2-0.10.9-sp1-6.0.0" }` (FACT, https://docs.succinct.xyz/docs/sp1/optimizing-programs/precompiles, 2026-09-07). RISC Zero equivalents: p256/v0.13.2-risczero.1 and sha2-v0.10.8-risczero.0 (FACT, https://dev.risczero.com/api/zkvm/precompiles, 2026-09-07).

Guest (new crate, e.g. klartext-verifier/pid-proof/program):
1. Inputs (private): the SD-JWT presentation string (issuer JWT, disclosures, KB-JWT), anchor certificate DER, bound address, nonce salt, now. Public output: sha256(anchor DER), sha256(vct), over18, address, nonce, exp.
2. Checks: split on `~`; base64url decode; parse header for x5c and alg ES256; parse leaf with x509-cert; verify leaf signature under anchor key (p256); verify issuer JWT signature with leaf key; recompute disclosure digests and find `age_equal_or_over` `18` == true in `_sd`; parse cnf.jwk; verify KB-JWT with cnf key; check sd_hash == sha256(issuer JWT ~ disclosures ~); check nonce == sha256(address || salt) and aud; check exp > now. Commit public values with sp1_zkvm::io::commit_slice (ABI encoded via alloy-sol-types, as in the `cargo prove new --evm` template).
3. Host: after the existing verify_pid_presentation_full passes, build stdin, call ProverClient::from_env().prove(&pk, &stdin).groth16(). Env SP1_PROVER=cpu for laptop, SP1_PROVER=network plus NETWORK_PRIVATE_KEY for the prover network.
4. Contract: registry.attest(bytes publicValues, bytes proofBytes) calls ISP1Verifier(0x397A5f7f3dBd538f23DE225B51f532c34448dA9B).verifyProof(PROGRAM_VKEY, publicValues, proofBytes), decodes the tuple, stores the EligibilityDecision keyed by address with expiry and the anchor hash as policy input. Groth16 gateway on Sepolia (chain 11155111): 0x397A5f7f3dBd538f23DE225B51f532c34448dA9B; PLONK gateway: 0xd685a80aF2d1761648e56716af4868d850Dae49B (FACT, https://docs.succinct.xyz/docs/sp1/verification/contract-addresses, 2026-09-07). The same page says the officially supported versions are V5.x.y and V6.1.0 (Hypercube); whether a 6.5 to 6.7 sp1-sdk proof routes on Sepolia is unverified, so pin sp1-sdk to a version the gateway lists.

Toolchain facts (this laptop, 2026-09-07): Apple M3 Max, 128 GB RAM, Docker at /usr/local/bin/docker, cargo 1.92, cargo-prove installed but from 2025-10-07 (pre-6.x, run `sp1up`), rzup with rust 1.91.1 and r0vm present. SP1 releases: v6.7.0 2026-09-07, v6.6.0 2026-09-02 (FACT, gh api). RISC Zero latest v3.0.6 2026-07-17.

Proving time: no laptop figure exists for this guest. Reference points: zk-X509 (SP1, Groth16, arXiv 2603.25190, 2026-03-26) reports 11.8M cycles for one P-256 ECDSA verification and about 300K gas on-chain (CLAIM, whether the precompile was used is not stated). Three verifies plus hashing should land in the low tens of millions of cycles (OPINION, measure it). zkbenchmarks.com (2025-03) shows SP1 CPU at roughly 10M keccak cycles in about 2 minutes on a 64-core EPYC; the M3 Max will be slower: unverified. Fallback: Succinct Prover Network, open access, requester key via `cast wallet new`, pay with PROVE on Ethereum mainnet, sp1-sdk >= 6.1.0, base fee example 0.2 PROVE, default timeout 300 s (FACT, https://docs.succinct.xyz/docs/sp1/prover-network/quickstart, 2026-09-07).
