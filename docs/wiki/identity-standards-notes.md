# Identity standards notes

This file holds the detail and the verbatim quotes behind /Users/bioharz/git/ethglobal/nachweis/wiki/identity-standards.md. Labels: FACT (verbatim from a fetched page or measured locally, URL and date given), CLAIM (stated by a source we did not confirm on an official page), OPINION (ours), unverified (no source found). ## 0. What the toolkit consumes today (the yardstick)

- FACT: verifier-service answers an OpenID4VP request with DCQL for an SD-JWT VC PID, vct urn:eudi:pid:de:1, checks the x5c chain to the sandbox trust anchor, the disclosure digests, the KB-JWT holder binding, nonce and audience (/Users/bioharz/git/ethglobal/nachweis/wiki/architecture.md, "Input").
- FACT: the Noir circuit pid-sdjwt assumes an ES256 issuer signature over the SD-JWT, SHA-256 disclosure digests, the issuer key pinned as issuerKeyHash (sha256 of the SEC1 key read off x5c[0]), the vct fragment, the KB-JWT nonce as sha256(address20 || challenge32), and the header field order of the Bundesdruckerei issuer (x5c, kid, typ, alg) with a header window that tolerates other orders (/Users/bioharz/git/ethglobal/nachweis-app/circuits/README.md lines 60 to 144). It does not parse X.509; the contract pins the key hash. Consequence (OPINION): any SD-JWT VC signed with ES256 and SHA-256 digests whose issuer key we can pin is in reach of the same circuit, whatever the issuer's trust mechanism (x5c chain, DID document, trust list), because the chain check happens off circuit in verifier-service and the circuit only sees the key.
- FACT: the pre-existing verifier-zk crate implements "The remote OpenID4VP `mso_mdoc_zk` response path, end to end" with system "longfellow-libzk-v1", a circuit registry, and issuer trust from "a configured trust anchor" where "`msoX5chain` holds EXACTLY one certificate (the leaf)" (/Users/bioharz/git/eudi-wallet-hackathon/verifier/verifier-zk/src/response.rs line 1 and 969, registry.rs line 22, trust.rs lines 1 to 10). The recorded demo bound docType eu.europa.ec.eudi.pid.1 and age_over_18 = true (docs/evidence/zk-demo/03-verifier-result-page.html in that repository). The circuit takes no namespace public input (finding 1 of that page). verifier-core contains no mdoc handling (grep for mdoc and 18013 in verifier-core/src returns nothing; the only hits are the zk handlers in verifier-service).
- FACT: the on-chain side takes any IProofVerifier; the registry binds subject, policyId, bits, expiry as the first four public inputs (architecture.md, "Proof interface"). An mdoc or zkPassport route changes the verifier contract, not the registry or the consumers.

## 1. Base standards

- FACT: "OpenID for Verifiable Presentations 1.0", "Published: 9 July 2025 Status: Final". Appendix A "OpenID4VP over the Digital Credentials API" defines the exchange protocol values "Unsigned requests: openid4vp-v1-unsigned", "Signed requests (JWS Compact Serialization): openid4vp-v1-signed", "Multi-signed requests (JWS JSON Serialization): openid4vp-v1-multisigned". Format identifiers in the text: dc+sd-jwt, mso_mdoc, ldp_vc, jwt_vc_json (https://openid.net/specs/openid-4-verifiable-presentations-1_0.html).
- FACT: W3C "Digital Credentials", "W3C Working Draft 04 September 2026", Federated Identity Working Group. The API lets "user agents to mediate the presentation and issuance of digital credentials, such as a driver's license, government-issued identification card, or other types of digital credential". Protocols named: org-iso-mdoc (implementing "ISO/IEC 18013-7:2025 ISO-compliant driving licence, Part 7: Mobile driving licence (mDL) add-on functions"), openid4vp-v1-unsigned, openid4vp-v1-signed, openid4vp-v1-multisigned, issuance openid4vci-v1 (https://www.w3.org/TR/digital-credentials/).
- FACT: ISO/IEC 18013-7:2025 is published; "ISO/IEC 18013-7 Annex B specifies a profile for OpenID4VP"; a third edition "aims to add OpenID4VP and HAIP solution running over a (browser) API" with planned publication "2026-12-21" (https://github.com/eu-digital-identity-wallet/eudi-doc-standards-and-technical-specifications/issues/1). iso.org returned HTTP 403 to our fetch, so edition wording on the official host is unverified. CLAIM (MATTR Learn, search summary): Annex C covers mdoc over the DC API on iOS and Safari, Annex D OpenID4VP over the DC API; do not quote as ISO text.
- FACT: EUDI PID rulebook v1.3 (6 Nov 2025): a PID may comply with ISO/IEC 18013-5 (doctype and namespace eu.europa.ec.eudi.pid.1) or with SD-JWT VC (vct per Topic 3) (https://raw.githubusercontent.com/eu-digital-identity-wallet/eudi-doc-attestation-rulebooks-catalog/main/rulebooks/pid/pid-rulebook.md lines 12, 32, 154 to 156).
- FACT: Longfellow README: "The Longfellow library enables the construction of zero-knowledge protocols concerning legacy identity verification standards such as the ISO MDOC standard, the JWT standard, and W3 Verifiable Credentials." License Apache 2.0, eprint 2024/2010, IETF draft-google-cfrg-libzk (https://raw.githubusercontent.com/google/longfellow-zk/main/README.md lines 4 to 11). Shipped circuits for SD-JWT: unverified; every deployment we found (Google Wallet, EU age verification app, verifier-zk) uses the mdoc circuits.
- FACT: Chrome "Digital Credentials API shipped" in Chrome 141 (blog 2025-10-03), "compatible with various presentation protocols, for example, OpenID4VP and Annex C of ISO 18013-7", naming openid4vp-v1-unsigned and org-iso-mdoc; Android same-device and desktop cross-device; iOS 26 via Safari (https://developer.chrome.com/blog/digital-credentials-api-shipped).
- FACT: WebKit: "Starting in Safari 26 on macOS 26, iOS 26, and iPadOS 26, we're introducing support for the W3C's Digital Credentials API." Request format "ISO/IEC 18013-7 Annex C and ISO/IEC 18013-5"; only org-iso-mdoc, no OpenID4VP, no SD-JWT on that page (https://webkit.org/blog/17431/online-identity-verification-with-the-digital-credentials-api/).

## 2. Switzerland (swiyu, federal e-ID)

- FACT: "The e-ID Act was narrowly approved in the referendum on September 28, 2025, with 50.39 percent voting in favor." "The e-ID is expected to go live on December 1, 2026." "Providers will be required to register their desired data queries and their purpose in advance in a publicly accessible federal register." "The e-ID will be technically unlinkable from the moment it is introduced." (https://www.eid.admin.ch/en/akzeptanz-der-e-id-mit-zusaetzlichen-massnahmen-staerken-e, page dated 2026-02-25). The same page says only legally authorised providers may retrieve the AHV number and the wallet blocks other requests.
- FACT: "the implementation of unlinkability can only take place in a second phase, after the introduction of e-ID. It is now clear that unlinkability will be implemented as soon as e-ID is introduced (in the third quarter of 2026 at the earliest)." "The white paper describes how unlinkability can be implemented using batch issuance." (https://www.eid.admin.ch/en/so-wird-die-e-id-unverknuepfbar-e, 2025-06-18). The two official dates (Q3 2026 at the earliest, 1 December 2026 expected) come from pages eight months apart; use the later one.
- FACT: batch issuance concept: "generate, for a given holder, several key pairs (and so several SD_JWT) for the same set of attributes and to use a key pair only once" and "With such a key management, it is possible to avoid tracking and use an ECDSA key pair only once." (https://raw.githubusercontent.com/swiyu-admin-ch/community/main/tech-concepts/e-id-key-management-batch-issuance-and-renewal.md lines 112 and 150). No BBS, no zero-knowledge on that page. Unlinkability is by one-time ECDSA credentials, not by anonymous credentials (OPINION on the wording).
- FACT technology stack: "The swiyu Trust Infrastructure relies on verifiable credentials according to IETF SD-JWT VC currently in combination with the ECDSA signature scheme." Versions "SD-JWT VC – draft 4" and "SD-JWT draft 10". "OpenID4VP (credential presentation by the holder), supports a remote (where holder and verifier interact online) same-device and cross-device verification." DID method did:webvh; "Token Status List was selected". (https://swiyu-admin-ch.github.io/technology-stack/)
- FACT verification profile: "OpenID for Verifiable Credential Presentation (OID4VP) v1.0", DCQL ("vp_formats_supported is NOT SUPPORTED, credential format identifier is determined in DCQL query's format parameter"), "response_mode MUST be direct_post.jwt", "Verifiers MUST send Verification Requests as a JWT-Secured Authorization Request (JAR)", client_id "decentralized_identifier:did:webvh:...", format "dc+sd-jwt" with "ES256, EdDSA", "JWS algorithm MUST be ES256. Encryption MUST use only ECDH-ES with P-256 Keys with A256GCM algorithm". Digital Credentials API and ISO 18013-7 not mentioned. (https://swiyu-admin-ch.github.io/specifications/swiss-profile-verification/)
- FACT VC profile: typ "dc+sd-jwt"; "When used, the _sd_alg claim MUST be sha-256."; "JWS algorithm MUST use ES256."; kid "Must be an absolute kid as specified in swiss-profile-anchor" (a did:webvh key, no x5c); "The cnf claim with the jwk confirmation method MUST be used if the Issuer wants to enable Key Binding."; KB-JWT "aud: REQUIRED. The aud claim MUST be client_id that was sent in the JAR of the verifier." No mdoc, no BBS. (https://swiyu-admin-ch.github.io/specifications/swiss-profile-vc/)
- FACT Beta-ID: "The Beta-ID is a pseudo-identity credential that was created for test purposes within the Sandbox environment, holding the same identity attributes as the coming e-ID." "The service for obtaining a Beta-ID is open to anyone who is interested." vct "betaid-sdjwt"; claims include document_number, given_name, family_name, birth_date, age_over_16, age_over_18, age_over_65, age_birth_year, birth_place, nationality, portrait, personal_administrative_number, issuing_country, expiry_date; issuer DID did:tdw:...swiyu-int.admin.ch...; "don't take it as an official and valid identity credential for your productive business cases." (https://swiyu-admin-ch.github.io/cookbooks/how-to-use-beta-id/)
- FACT onboarding: through the "swiyu Service Portal": subscribe to three APIs, generate and upload a DID log with the DID Toolbox, create a proof-of-possession JWT, submit it to the trust registry; "for each DID costs will be charged" without figures; eligibility of foreign companies not stated (https://swiyu-admin-ch.github.io/cookbooks/onboarding-base-and-trust-registry/). The sandbox is "an open test environment where authorities, companies, and individuals can test the trust infrastructure under realistic conditions" (https://www.eid.admin.ch/en).
- FACT: "It is planned to gruadually develop Public Beta into an integration environment that is run in parallel and equivalent to the productive infrastructure from Go-live in 2026 onwards." and "the e-ID program is planning to upgrade most of the implemented specifications to newer and more mature versions until the Go-live" (https://swiyu-admin-ch.github.io/roadmap/).
- Circuit fit (OPINION, from the facts above and circuits/README.md): ES256, SHA-256 digests, KB-JWT with nonce and aud, dc+sd-jwt: the same shapes the Noir circuit and the SP1 guest parse. Differences to handle off circuit: the issuer key comes from a did:webvh DID document on the base registry instead of an x5c header (verifier-service resolves the DID, the contract pins the key hash as today); the vct fragment changes (betaid-sdjwt now, production vct unverified); the request must be a JAR with response_mode direct_post.jwt and a did:webvh client_id, which means our verifier needs its own DID on the swiyu base registry; the header field order differs from Bundesdruckerei's (the circuit's header window is designed for that, README line 91 to 93, but a Beta-ID vector has not been run: unverified). Unlinkability by batch issuance does not affect a relying party.

## 8. ICAO passport chip (the zkPassport route)

- FACT: "The ICAO Public Key Directory (PKD) is a central repository for exchanging the information required to authenticate electronic Machine Readable Travel Documents (eMRTDs)" (https://www.icao.int/security/fal/pkd/pages/default.aspx). Participants page shows 111 (https://www.icao.int/icao-pkd/participants); the fee schedule counts 107 participants at 2025-11-15 (https://www.icao.int/sites/default/files/2026-02/B-Fin-255-PKD-Fee-Schedule-2026_0.pdf, search summary, CLAIM). Master List: "contains the Country Signing Certificate Authority (CSCA) public key certificates of ICAO PKD members", 579 certificates, version of 15 July 2026, downloadable by the public under terms (https://www.icao.int/icao-pkd/icao-master-list). Private sector pilot since December 2021, 50 companies, "authorized entities are permitted to use PKD data obtained from the public PKD data download website and the public ICAO Master List download site"; a paid programme replaces the pilot, expected 2027 (https://www.icao.int/icao-pkd/private-sector-pilot).
- FACT (zkpassport.md, verified 2026-09-09): zkPassport proves over the chip's passive authentication chain (CSCA to DSC to SOD) in Noir on the phone; the certificate registry on Sepolia holds 586 certificates from 140 countries; the root verifier is at 0x1D000001000EFD9a6371f4d90bB8920D5431c0D8 on mainnet, Sepolia and Base; age at least 18 with bind user_address and chain; the adapter is built in contracts/src/zkpassport. This is the route with no relying-party registration at all: the trust anchor is the country's CSCA, mirrored by zkPassport's registry.
- Formats: the chip carries LDS data groups under Doc 9303 (X.509 CSCA and DSC, SOD signature), not SD-JWT or mdoc. Our Noir SD-JWT circuit does not apply; zkPassport's circuits do, and the toolkit consumes their proof through the adapter.

"From March 24, 2025, My Number Card will be able to be used as a driver's licence"; rental car shops read it with a PIN-protected app; the Android smartphone certificate cannot act as the licence (https://www.digital.go.jp/en/policies/mynumber/drivers-license). "My Number Card on iPhone Service Launched", start 2025-06-24 (https://www.digital.go.jp/en/policies/mynumber, https://services.digital.go.jp/mynumbercard-iphone/news/79897b6ef9f29d5b27a3d/). Apple lists Japan My Number Cards in the Verify with Wallet age example (section 6).
- mdoc, SD-JWT VC, OpenID4VP, trust list download, age predicate: unverified on official pages. CLAIM (Nikkei, PocketSign): a smartphone My Number Card and licence on ISO/IEC 18013-5 targeted for end of 2026.

## 12. South Korea (mobile ID, DID based)

"블록체인에는 '나'를 구별하고 '내' 정보의 진위만 검증할 수 있는 암호화된 자물쇠만이 등록됩니다." and "신원증명을 위해 필요한 정보만 골라서 제공할 수 있습니다." (https://www.mobileid.go.kr/mip/hps/svcIntrcn/svcIntrcnMobileIdn.do). Private wallets: Samsung Wallet now, banks and Naver, Toss, Kakao to follow (https://www.mobileid.go.kr/mip/hps/main.do).

## 13. Taiwan (Digital Identity Wallet, moda)

- FACT (API specification, revision 1.2 of 2025-12-12, https://raw.githubusercontent.com/moda-gov-tw/TWDIW-official-app/main/Docs/TWDIW_API_Specification.md, re-read by the teammate): the ecosystem exchanges VCs and VPs "以符合 OID4VCI 與 OID4VP 國際標準的方式" (line 37); the issued credential is "一組 SD-JWT 格式的 VC Token" (line 332) with header "jku（金鑰位置）、kid（金鑰識別碼）、typ（vc+sd-jwt）、alg（ES256）" and payload "sub（持有者 DID）、iss（發證者 DID）... credentialSubject（VC 主體資料，為 SD-JWT 結構）、credentialStatus（狀態清冊資訊）" (lines 353 to 354); the verifier module "由數位發展部提供，並部署於驗證端之伺服器環境，實作 OID4VP 標準 API" and supports "指定選擇性揭露欄位" (lines 121 to 123); the flow returns a QR code and a deep link "openid4vp://" (lines 884, 1094); errors name "presentation_definition" (line 917), so the profile is Presentation Exchange, not DCQL; the result carries "holder_did": "did:key:abcd1234" (line 988). The VP "再次加上持有端的簽章與時戳" (line 66); whether that is a KB-JWT: unverified. _sd_alg: not stated on the fetched page (unverified).
- FACT README (https://raw.githubusercontent.com/moda-gov-tw/TWDIW-official-app/main/README.md): "以 OID4VC / OID4VP 為核心的可信賴身份服務", components "驗證端 OID4VP 服務", "驗證端 VP 服務: 驗證 VP/VC 與 SD-JWT，支援選擇性揭露", iOS SDK "Secure Enclave 之 DID 金鑰管理", MIT licence.
- FACT press release (https://moda.gov.tw/en/press/press-releases/15752): the sandbox opened "Monday, March 31, 2025, at 10:00 AM" to "Public and private sector organizations, businesses, academic and research institutions, civil groups, and individuals", at https://verifier-sandbox.wallet.gov.tw and https://issuer-sandbox.wallet.gov.tw. wallet.gov.tw itself returned a Cloudflare 403 to our fetch. CLAIM (ithome.com.tw/news/173834): trust lists planned. CLAIM (tahr.org.tw/news/3845): trial operation from end of 2025 with no dedicated statute yet. Age predicate, a national natural-person credential's claim list, foreign verifier eligibility: unverified. Google Wallet lists "Taiwan (ID Pass)" (section 6).
- Circuit fit (OPINION): SD-JWT with ES256 and a JWKS-hosted issuer key is the shape the Noir circuit parses, with the issuer key pinned by hash as today; open points are the digest algorithm, the holder-binding form and the claim names, all unverified until a sandbox credential is read.
