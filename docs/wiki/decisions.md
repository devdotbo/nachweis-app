## 2026-09-07 night: no Android phone (FACT, builder decision on the lead's recommendation)

The builder's Android phone is not available. Decision: do not buy one. Reasons: the official test wallet run and the presentation beat work on the iPhone (birthdate fallback for the iOS nested age quirk); the SP1 proof is server-side; the client-side Noir proof does not need a phone because the blind relay encrypts the wallet response to a key held by the user's device, and that device is the laptop for the submission (decrypt, prove in about 3.5 s, submit; the server never sees names). On-phone proving (WP5, Mopro) becomes an optional bonus, not a gate. WP5 is redefined as a desktop companion prover: consume the relay pickup, decrypt ECDH-ES A128GCM with the client key, run gen-prover and bb prove, submit through the bridge or directly via NoirPidVerifier.


## 2026-09-07 night: buy a Pixel 10 for on-phone proving (FACT, builder decision)

The builder buys a Pixel 10 (returnable). Reason: the only reference implementation of on-phone Noir proving for SD-JWT credentials is Android (eid-privacy zkp-android, Mopro); no iOS app exists, so Android is the shorter path to a measured on-phone proof. The laptop companion (WP5) stays the fallback client device for the submission. WP5-android: fork zkp-android, align the Noir toolchain version between the app's noir-rs and our circuit artifact, add relay pickup, JWE decryption and witness generation, prove on the emulator first, then on the Pixel 10 when it arrives. iPhone on-phone proving (WP12) stays optional.


## 2026-09-08 (builder as moderator, lead)

- Main path is iPhone plus Mac (FACT, builder message 2026-09-08: the Android phone cannot be found; GPT review: no Android or on-phone requirement in the Uniswap prize or the judging criteria). Route: official iPhone test wallet, blind relay, client-side Noir proof on the Mac companion, issuer approval, subscribe, swap, revoke. Native phone proving (WP5-android, WP12) stays optional. An Android requirement is raised only against a concrete failed integration gate (for example the iOS wallet cannot present the age claim or does not encrypt to a client key) or a demonstrable improvement after the main flow passes. Rejected: buying or borrowing an Android phone now.
- Issuer approval is enforced on chain (lead design, from the independent review in wiki/handoff-fable-2026-09-08.md). The registry keeps two facts per (subject, policyId): evidence (attestWithProof stores it, permissionless) and approval (a separate `approve` by an operator; attestByOperator implies approval). isEligible requires both, plus not revoked and not expired. Revoke clears approval; reapproval requires an operator. The proof path cannot reopen a revoked record. Bridge, app, scripts and tests follow (WP16). Rejected: delaying the UI only (does not establish the on-chain policy); auto-approval on proof (contradicts the product sentence in product.md).
- Privileged bridge operations (attest-operator, approve, revoke) require a bearer token; the verifier's bridge-mode result endpoint requires a shared token and returns no names by default (WP16, WP17). Rejected: unauthenticated issuer routes on a public origin.
- Work from the review is run as five parallel packages: WP16 issuer approval, WP17 service boundaries and trust contract, WP18 G0 runbook, WP19 evidence and submission repair, WP20 Attestat public copy and hosting preparation. Integration, merges and any deployment stay on the lead's main thread.
- Public surfaces say Attestat with attestat.dev as canonical URL; repository names, package and crate names, `nachweis:session:`, `nachweis.pid.over18.v1` and the `nachweis://handoff` scheme stay unchanged for this submission (accepted from the GPT review; recorded in name-and-domains.md as the rename scope).
- G0 result (FACT, run of 2026-09-08 evening, record in nachweis-app/docs/evidence/g0-2026-09-08.md): the official test wallet encrypts to the client-supplied key, so the client-side Noir route with the blind relay stays the main path; the SP1 fallback is not selected. The proof over the real presentation waits on WP22 (header window). Decision point after WP0: go.
- Browser proving becomes the default investor path in the web app (lead, 2026-09-08 night, on the WP26 spike: 21 s click to verified in Chrome on the M3 Max, same VK, byte-identical public inputs, native verify passes). The laptop companion and the phone handoff stay as selectable paths; iOS Safari falls back to the handoff (bb.js 1 GiB wasm cap, unverified). Rejected: keeping the CLI companion as the only client (an install step in the demo), and native phone proving as the main path (no device evidence yet).
