# Handoff for GPT 6 Astra (WP4 and WP5)

Self-contained. Read this page only, then the two source repositories named below. Rules: English, absolute paths, no em dashes, no emojis, say "unverified" instead of guessing, label FACT, CLAIM, OPINION. Report back in the return format at the end.

## What Nachweis is, in three sentences

Nachweis helps token issuers accept EUDI identity evidence and apply their approval to customers' linked crypto wallets, without putting identity documents on chain. The official German test wallet (sandbox, sample identity, not a real state-issued ID) presents an SD-JWT PID to the issuer's verifier; the issuer approves; an EligibilityDecision (policyId, bits, tier, expiry, statusRef) is stored on Sepolia per crypto address. Your job is the zero-knowledge proof that turns "our server says so" into "the chain verified a proof": a Noir proof, made on the investor's phone, that a valid PID bound to this address says over 18.

## Your deliverables

1. Circuit: the eid-privacy Noir SD-JWT circuit adapted to the German PID claim shape, in nachweis-app/circuits (new branch in nachweis-app, small commits).
2. Negative tests (mandatory, listed below), all failing correctly, with a test runner and a log in the repo.
3. Solidity verifier (UltraHonk, generated by bb) implementing the Nachweis IProofVerifier interface, plus a Foundry test that calls AttestationRegistry.attestWithProof with a real proof.

## German PID claim shape (FACT, klartext-verifier/verifier-core/src/pid.rs:60-107, read 2026-09-07)

Format dc+sd-jwt (PID_FORMAT, pid.rs:20), vct urn:eudi:pid:de:1 (PID_VCT, verifier-core/src/lib.rs:30), age thresholds [12, 14, 16, 18, 21, 65] (AGE_THRESHOLDS, pid.rs:23). Claim paths from pid_claim_model():

    family_name                     mandatory, correlatable
    given_name                      mandatory, correlatable
    birthdate                       mandatory, correlatable
    place_of_birth / locality       mandatory, correlatable
    nationalities                   mandatory, correlatable
    address / resident_country      optional, correlatable
    address / resident_city         optional, correlatable
    address / resident_postal_code  optional, correlatable
    address / resident_street       optional, correlatable
    family_name_birth               optional, correlatable
    given_name_birth                optional, correlatable
    date_of_expiry                  mandatory
    issuing_authority               mandatory
    issuing_country                 mandatory
    age_in_years                    optional
    age_birth_year                  optional, correlatable
    age_equal_or_over / <t>         optional, one per threshold t in AGE_THRESHOLDS

The registered minimal request (pid_dcql_minimal, pid.rs:139-146) asks for given_name, family_name and age_equal_or_over/18. Caveat (FACT, verdict page 2026-09-06): the address.resident_* paths in pid.rs follow the mdoc naming; the German SD-JWT reference uses address.country, address.locality, address.postal_code, address.street_address. Irrelevant for the over-18 statement, relevant if you ever touch residence.

Minted vector shape (FACT, decoded 2026-09-07 from nachweis-app/prover-sp1/fixtures/synthetic-over18.sdjwt): issuer JWT header {alg ES256, typ dc+sd-jwt, x5c}; payload keys _sd, _sd_alg sha-256, age_equal_or_over (an object with its own _sd array), cnf.jwk, exp, iat, iss, nbf, vct; presented disclosures given_name, family_name and the nested disclosure "18" with value true; KB-JWT payload keys aud, exp, iat, nonce, sd_hash. The nested age_equal_or_over object is the main difference to the swiyu vector: over-18 is a disclosure named "18" anchored in age_equal_or_over._sd, not a top-level claim.

## The statement to prove (agree with the contracts)

Private inputs: the full presentation (issuer JWT, disclosures, KB-JWT), the issuer public key, the challenge. Checks, identical to the SP1 lib:

1. Issuer JWT alg ES256; signature over header.payload verifies under the issuer key; vct == urn:eudi:pid:de:1; _sd_alg sha-256.
2. Every presented disclosure hashes (base64url(sha256(disclosure))) into a signed _sd array, top level or nested through an accepted disclosure.
3. over18 := the age_equal_or_over object has a disclosure named "18" with value true anchored in its _sd; else false.
4. Holder key from cnf.jwk (P-256); KB-JWT alg ES256, typ kb+jwt, signature verifies under it.
5. KB-JWT aud == expected; sd_hash == base64url(sha256("issuerJwt~d1~...~dN~")).
6. Nonce and address binding: KB-JWT nonce == lowercase hex, no 0x prefix, 64 chars, of sha256(subject || challenge), where subject is the 20-byte Ethereum address and challenge is the 32-byte server challenge. This is the definition the relay branch and the contracts use; do not change it.
7. expiry := min(issuer exp, KB-JWT exp), 0 if neither present. No wall clock in the circuit; the contract compares expiry with block.timestamp.

Outside the circuit (state it in your README): x5c chain to the trust anchor (the contract pins issuerKeyHash), status list, freshness window, the issuer's approval.

Public inputs, in the order the registry binds them (FACT, nachweis-app/contracts/src/AttestationRegistry.sol attestWithProof):

    publicInputs[0] = bytes32(uint256(uint160(subject)))
    publicInputs[1] = decision.policyId
    publicInputs[2] = bytes32(decision.bits)          // bit 0 = over 18
    publicInputs[3] = bytes32(uint256(decision.expiry))

    interface IProofVerifier {
        function verify(bytes calldata proof, bytes32[] calldata publicInputs) external view returns (bool);
    }

Your Solidity verifier is set per policyId by the registry owner. Follow the pattern already merged for SP1 (FACT, nachweis-app/contracts/src/sp1/Sp1PidVerifier.sol, 2026-09-07): the adapter holds gateway or verifier address, verification key, issuerKeyHash, vctHash and policyId as immutables; the proof argument is abi.encode(bytes publicValues, bytes proofBytes); the adapter checks publicInputs[1] == its POLICY_ID (default keccak256("nachweis.pid.over18.v1")), derives bits as BIT_IDENTITY (1) | BIT_OVER_18 (2) from the proof's over18, and exposes nonceOf(proof) so the registry consumes the nonce (NonceConsumed on replay). Use a distinct policyId for the Noir route so both adapters can coexist. Do not change AttestationRegistry.PUBLIC_INPUTS_LENGTH without the lead.

## Mandatory negative tests

Each is a mutated vector that must fail to prove or must fail verification; record which:

1. Issuer signature tampered (one byte in the signature).
2. Issuer JWT signed by a different P-256 key (wrong issuer).
3. vct changed to another value.
4. Disclosure not anchored in any _sd (forged disclosure).
5. age_equal_or_over "18" disclosure with value false, and a vector with no "18" disclosure at all (over18 must be 0, and the registry must refuse bit 0).
6. KB-JWT signed by a key other than cnf.jwk (holder binding broken).
7. sd_hash mismatch (a disclosure removed after the KB-JWT was signed).
8. Nonce for a different address (address substitution), and nonce for a different challenge (replay).
9. Expired issuer JWT and expired KB-JWT (expiry propagates; contract rejects when past).
10. Proof replayed against a revoked decision (contract-level test: attestWithProof after revoke must revert).
